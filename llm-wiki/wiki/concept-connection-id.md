# Concept: connection id

**Summary**: UUID that identifies one configured backend server. A Containerus user can have many — each with its own URL, tokens, user, projects, permissions. `connectionId` is the routing key into `BackendService._connections`, and it's what `_systemOwnership` maps system ids to.

**Sources**: `src/app/core/services/backend.service.ts`, `src-tauri/src/commands/backend.rs`.

**Last updated**: 2026-04-16

## Where it lives

- SQLite `backend_connections.id` (desktop) — persisted.
- `BackendService._connections[i].id` (frontend memory) — reactive signal.
- `CredentialVault.backend_tokens[connectionId]` — keyring-stored access + refresh tokens.
- `BackendService._systemOwnership: Map<systemId, connectionId>` — system routing.

## Lifecycle

Generated by the frontend when the user clicks "Add backend" (`crypto.randomUUID()`). Persisted as soon as the URL probe succeeds (via `save_backend_connection` Tauri command). Never reissued — rotating ids would break the `_systemOwnership` map.

## Per-connection state

For each connection the service holds:

```ts
{
  id: string,
  serverUrl: string,
  label: string,
  tokens?: { accessToken, refreshToken },
  user?: { id, email, is_company_admin, ... },
  projects?: Project[],
  projectPermissions?: Map<ProjectId, Set<string>>,
  status: 'connected' | 'disconnected' | 'connecting' | 'error',
}
```

All mutations go through `BackendService` methods (`loginToBackend`, `logoutFrom`, `loadProjectsFor`, etc.) so the vault stays synced.

## URL parameterization

Backend routes put `connectionId` first:

- `/backends/:connectionId`
- `/backends/:connectionId/projects/:projectId`
- `/backends/:connectionId/projects/:projectId/environments/:envId`

All backend-specific pages extract it from the route and pass into `BackendService.requestFor(connectionId, ...)`.

## Comparison with system id

| | system id | connection id |
|---|---|---|
| Identifies | a host Containerus talks to | a server it gets hosts from |
| Scope | local or backend | frontend only |
| Persistence | SQLite `systems` + Postgres `systems` | SQLite `backend_connections` + keyring vault |
| Routing question | local vs HTTP? | which backend? |

See [[concept-system-id]] for the counterpart.

## Auto-reconnect ordering

At boot, `BackendService.loadPersistedConnections()` iterates every connection. For each:
1. If `_userLoggedOut.has(id)` → skip.
2. If vault has tokens → try `refreshTokenFor(id)`.
3. If that succeeds → `loadProjectsFor(id)` + `loadPermissionsFor(id)` → status `connected`.
4. If refresh fails (e.g., refresh token expired) → status `disconnected`, keep URL + label, clear tokens.
